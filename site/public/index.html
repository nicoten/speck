Start a change

Describe the idea and Speck hands it to Claude, which writes the proposal, the specs, the design and the task list — then stops. Planning only, by OpenSpec's own rules: nothing in your code is touched until you have read what the change intends to do.

Read it in order

Your documents are grouped by where they sit in the workflow — the project's own docs, the changes in flight, the specs they will become, the archive behind them. Inside a change, the order comes from the schema your project declares, so proposal → specs → design → tasks for the stock workflow and something else entirely for yours. Every document gets a number in one sequence, and ⌘[ and ⌘] walk it end to end.

An artifact the schema expects but nobody has written yet stays on the rail as an open circle, because in a spec-driven workflow that gap tells you something. It takes no number, so paging never lands on an empty page.

Apply it

The task list tells you which ones are still open, not just that three of twenty-one are done, and a change's dashboard says the same thing beside its artifacts. Apply from either and the session runs inside Speck, streaming every file it reads and every command it runs into a panel you can stop mid-task. Or hand the run to your terminal and approve each step yourself.

Progress arrives on its own either way. The agent ticks boxes in tasks.md, Speck notices the file change, and the count climbs in the sidebar while you carry on reading. You can tick one yourself when you have checked it by hand.

Verify, then archive

Emphasis moves as the work does. Apply leads while tasks remain, verify takes over once they are all ticked, and archive stays quiet — it rewrites your main specs and moves the change, which is not a button to lean on.

Archive is better run in your terminal, and Speck says so before you start it: the workflow needs to ask how to merge the change's delta specs into your main specs, and a session running headless has nobody to ask. Once it lands, the next change starts where this one did.

What Speck itself writes

An app that summons an agent into your repository owes you a straight answer about what it touches. Speck writes one character: a task's checkbox, on one line, in a change's own tasks.md. Specs, proposals and your code are refused by path before anything is read, and there is no filesystem write capability in the app's configuration at all.

The task is addressed by its text, and by which occurrence where the wording repeats — never by line number, because an agent may have rewritten the file between you reading it and clicking the box, and a line number would then tick the wrong task with nothing to notice. If the task is no longer there, the write fails and says so. The rest of the file comes back byte for byte.

The same honesty applies where Speck is guessing. OpenSpec records no pull request, so any link to one is inference, and the app says as much rather than presenting a guess as a recorded fact. It looks for a branch named after the change, then for pull requests touching the change's own files, and shows every match instead of picking one — the newest commit under an archived change is the commit that archived it. When it finds nothing, it tells you what it looked for.
